# 9. Purchase Booking (PB)

PB is the final step of the purchase chain: **PO → GP → GRN → QC → PB**.

The ERP uses an **async SUBMIT pipeline** — the `POST` returns `201` immediately (provisional ack only), then a background SSE stream runs 28 steps that actually commit the record. **A `201` response does NOT mean the PB succeeded.** You must watch the SSE steps; the record only appears in the PB listing after `PURCHASE_BOOKING_COMPLETED`.

---

## 9.1 Endpoint

```
POST /procure_to_pay/purchase-booking/
     ?screenName=Purchase%20Booking
     &submission_id={{pur_pb_submission_id}}
     &request_method=SUBMIT
```

SSE stream (poll after 201):
```
GET /notification/api/transactions/{{pur_pb_submission_id}}/events/
```

The Postman collection **does not poll SSE** — check the ERP UI (Purchase Booking listing) to confirm the record appeared. If it doesn't appear within ~10 seconds the pipeline failed; see §9.6.

---

## 9.2 What `pur_qc_lines` contains

The pre-request reads lines from `pur_qc_lines`, which is set by **Create QC's test script**:

```js
pm.environment.set('pur_qc_lines', JSON.stringify(reqBody.qc_details));
```

So `pur_qc_lines` holds the **QC request body lines** — the same objects sent to create the QC. Key fields used in PB:

| Field | Used for |
|---|---|
| `txn_currency_amount` | `txn_currency_amount_detail` (post-discount net amount) |
| `c_d_deduction` | `txn_currency_discount_amount_details` (monetary cash discount) |
| `alternate_accepted_qty` | `alternate_net_qty` + `rate` computation |
| `grn_qty` | `alternate_qty`, `alternate_gate_pass_quantity` |
| `base_rate`, `empty_bag_weight`, `empty_bags_txn_amount` | pass-through to PB line |
| `discount_rate` | `discount_percentage` |

---

## 9.3 Critical field rules (all hard-learned from accounting failures)

### GST is **required** for non-zero tax rates

`pur_tax_rate` (set during Discover from the item's HSN tax map) controls GST. **If 0, no GST is applied — and if the item master has a non-zero tax rate the accounting will fail.**

The ERP's CALCULATION step uses the **item master tax rate** to compute the DR (inventory) side of the journal entry. If your payload has no GST, the CR side (AP + GST = 0) won't match the DR side → `Debit credit SUM is not zero`.

Set `pur_tax_rate` correctly in the environment before running Create PB.

### `total_txn = amount_detail + gst` — no discount subtraction

`txn_currency_amount` from the QC is **already post-discount** (the cash discount was subtracted when the QC was created). The PB formula is:

```
total_txn = amount_detail + gst_amount          ← correct
total_txn = amount_detail - discount + gst      ← WRONG (double-discounts)
```

### Amounts are **floats**, not `"0.000"` strings

The CALCULATION step parses amounts numerically. String amounts (`f3()`) cause silent truncation that misaligns DR/CR totals.

### Zero GST slots → `null`, not `0.0`

When IGST is used, `cgst_amount` and `sgst_amount` must be `null`. Sending `0.0` or `"0.000"` for unused GST components causes the validator to attempt a zero-amount posting.

### `round_off_credit_amount` / `round_off_debit_amount` → `null`

The validator fires only on non-null values: *"Amount should be greater than 0"*. Sending `0.0` or any random value triggers it. Both must be `null` together — one null and one non-null crashes the server with 500.

### `posting_status` → `""` (empty string, not `"Post"`)

### `section_ref_id` → `"0"` (string, not integer `0`)

### `tds_amount` → `null` (not `"0.000"`)

### `purchase_booking_ref_type` → `144` (required field, must be present)

### `conversion_rate` → `"1"` (string, not float `1.0`)

### `uom_conversion` → string (`"1.0"`, not float `1.0`)

## 9.4 Pre-request field map

```
ENVIRONMENT VARS CONSUMED
  pur_pb_submission_id  — fresh UUID set at top of pre-request
  pur_qc_lines          — JSON array of QC detail lines (set by Create QC)
  pur_tax_rate          — item's GST rate (set by Discover; 0 = no GST)
  pur_qc_id / pur_grn_id / pur_po_id / pur_supplier_id
  pur_parameter1/2/5/6 / pur_base_currency / pur_txn_currency
  pur_supplier_payment_terms / pur_pb_payment_terms

COMPUTED PER LINE
  amountDetail        = qc.txn_currency_amount           (post-discount)
  gst                 = splitGst(amountDetail, taxRate, gstType)
  cashDiscount        = qc.c_d_deduction                 (informational only)
  totalTxn            = amountDetail + gst.tax_amount    (no discount subtracted)
  rate                = amountDetail / alternate_net_qty

HEADER AGGREGATES
  txn_currency_amount        = Σ amountDetail   (float)
  txn_currency_total_amount  = Σ totalTxn       (float)
  txn_currency_discount_amount = Σ cashDiscount (float)
```

## 9.6 Troubleshooting

### `Debit credit SUM is not zero` at step 21/22

The most common failure. The journal entry's DR and CR sides don't balance.

| Cause | Fix |
|---|---|
| **GST missing** — `pur_tax_rate` is 0 but item has 5% GST | Set `pur_tax_rate` to the correct rate (e.g. `5`) and re-run |
| `total_txn` double-subtracted discount | Pre-request was old version — reimport collection |
| Amounts sent as f3 strings instead of floats | Pre-request was old version — reimport collection |
| Non-null `round_off_debit/credit` | Pre-request was old version — reimport collection |
| Ghost PB left by a previous failed attempt (see §9.7) | Use a fresh QC (re-run the full chain from Create PO) |

### `Amount should be greater than 0` at INPUT_VALIDATION (step 5)

`round_off_debit_amount` or `round_off_credit_amount` is non-null and ≤ 0. The validator only fires for non-null values. Fix: both must be `null`.

### `500` response on POST (before SSE)

`section_ref_id` sent as integer `0` instead of string `"0"`. Or: ghost PB from a prior failed attempt has corrupted state for this QC — use a fresh QC.

### `201` response but PB never appears in listing

The SSE pipeline failed after `PURCHASE_BOOKING_SAVED`. The record is a **ghost PB** (§9.7). Check the ERP UI → Purchase Booking → look for a record with blank fields or a `FAILED` status.

### `Missing PB deps: pur_qc_lines (empty)`

Create QC did not run, or its test script failed. Run the full chain in order: Discover → Create PO → Create GP → Create GRN → **Create QC** → Create PB.

## 9.7 Ghost PBs

**What they are:** When `PURCHASE_BOOKING_SAVED` (step 17) succeeds but `PURCHASE_ACCOUNTING_POST` (step 21) fails, a DB row is written with the PB id (DB sequence consumed) but with null/blank accounting fields. These records are visible in the ERP only as ghost entries.

**Why they matter:** Subsequent attempts to create a PB for the **same QC** may fail — inventory may be partially reserved by the ghost, or the ERP may reject a second PB for the same QC. Symptoms: repeated 500 errors or repeated accounting failures even after fixing the payload.

**Fix:** Use a **fresh QC** — re-run the chain from Create PO to get a new QC with no history. Ghost PBs cannot be easily deleted from the UI.

**Prevention:** Get the payload right on the first attempt (see §9.3).

## 9.8 Environment variables set after success

Create PB's test script sets:
```
pur_pb_id    — id from the 201 response body
```

Note: the `id` in the 201 response is the provisional DB id. If the SSE pipeline fails, this id belongs to a ghost PB. Always verify the PB appears in the listing before trusting `pur_pb_id`.

## 9.9 Checking `pur_tax_rate`

`pur_tax_rate` is set by **Discover Context** from the item's HSN tax map. To verify:

1. Open the Postman environment.
2. Check `pur_tax_rate` has a non-zero value (e.g. `5`).
3. If it's `0` or missing: re-run **Discover Context**, or set it manually to match the item's GST rate.

Items that use IGST: set `pur_tax_rate = 5` (or the actual rate). Items with no GST: `pur_tax_rate = 0` is correct and PB will work without GST fields.
