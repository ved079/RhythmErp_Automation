## 8.1 Endpoints

| Request | Endpoint |
|---------|----------|
| List QC / Create QC | `GET/POST /procure_to_pay/quality-control/` |
| Get QC Detail | `GET /procure_to_pay/quality-control/{id}/` |
| CQP (per-item quality config) | `GET /core/dynamic-screen-wrapper/Commodity%20Quality%20Parameter/?page_number=1&page_size=500` |
| CQP detail | `GET /core/dynamic-screen-wrapper/Commodity%20Quality%20Parameter/{id}/` |
| Packages (bag types) | `GET /core/dynamic-screen-wrapper/Packages/` |

> QC schema (`/core/dynamic-screen/QC/`, 18 fields) has **no** bag-type dropdown — `type_of_bags_ref_id` lives on the nested `qc_bags_details` and is resolved from the **Packages** screen. The quality-parameter values come from the item's **Commodity Quality Parameter (CQP)** config, not from the QC screen schema.

## 8.2 Discover stages (QC's two FKs that used to be sniffed)

Previous versions **sniffed** `pur_qc_params` and `pur_bags_type_id` from an existing QC's `qc_parameter_details` via List QC's test script. That broke on fresh tenants (no stored QC). Both are now resolved by **Discover Context** — the last two stages of `discover()`, which run after the item is seeded (they need `pur_item_ref_id`):

### Stage A — Quality params: the item's CQP (`_resolve_cqp_params` mapping)

1. `GET Commodity Quality Parameter/?page_number=1&page_size=500` → walk every row, skip any whose listing `transaction_type` is not `Purchase` (avoids Spot/others).
2. For each candidate, `GET Commodity Quality Parameter/{id}/` and keep the first whose detail matches:
   - `item_ref_id === pur_item_ref_id`
   - `from_date` is absent or `<= today`
3. Flatten `children[0].details[]` (the quality-parameter tiers) into `pur_qc_params`:

```
{ item_quality_parameter_ref_id: p.quality_type, actual_value: p.min_quality_value, allowable_percent: 0.0 }
```

On 795, item **11** → CQP **#13** (`from_date 2026-06-23`, `transaction_type 154`) → **9 tiers**:

| quality_type | min_quality_value (actual_value) |
|--------------|----------------------------------|
| 1 | 1, 12.001, 27.001 |
| 3 | 3, 12.001, 24.6 |
| 2 | 2, 4.01, 6.02 |

Those are exactly the `qc_parameter_details` values stored on QC 2129 — CQP is the source of truth. If no active Purchase CQP exists for the item, `pur_qc_params` is left unset and Create QC falls back to generic `[1,2,3]` (see §8.4).

### Stage B — Bag type: the Packages screen (`_resolve_bags_type_id` mapping)

1. `GET /core/dynamic-screen-wrapper/Packages/` (no pagination params) → rows under `screenmatlistingdata_set` (fallback `rows`/`first_entries`).
2. Prefer a row whose `name`/`type_of_bags_ref_id` contains **jute/joot** (case-insensitive); else the first row.
3. `GET /core/dynamic-screen-wrapper/Packages/{id}/` → if `packages_line_details[0].type_of_bags_ref_id` exists use it, else use the row's own `id`.

On 795 the first row is **id 20 ("Roll")**, detail carries `type_of_bags_ref_id: 20` → `pur_bags_type_id = 20` (matches QC 2129's `qc_bags_details[0].type_of_bags_ref_id = 20`).

Both stages are guarded (`if (!pur_qc_params)` / `if (!pur_bags_type_id)`), wrap their API calls in try/catch, narrate into `pur_sniff_status` (`QC quality params from CQP #13 (item 11): 9 tiers`, `bag type 20 from Packages row 20 (Roll)`), and are recorded in `pur_ctx.qc = { params, bags_type }`.

## 8.4 QC math (pre-request, port of `_compute_qc_line_fields`)

Same math as before (see README "QC math") — the only change is *where the inputs come from*:

| Input | Before (sniff) | Now (Discover) |
|-------|----------------|----------------|
| `qc_parameter_details` | copied from an existing QC's `qc_parameter_details` | item's **CQP** tiers — verified 9-tier match |
| `type_of_bags_ref_id` | copied from an existing QC's `qc_bags_details[0]` | **Packages** screen → `pur_bags_type_id` |

`quantity_deduction` is computed per parameter row in the pre-request as `Math.ceil(deduction_weight)` where `deduction_weight = grn_qty × deduction_percent / 100`. Note: the ERP stores `population` of every CQP tier as its own row, so a CQP with N tiers produces N `qc_parameter_details` rows (verified: 9 tiers → 9 stored rows).

Fallbacks when Discover found nothing: `pur_qc_params` unset → generic `[{item_quality_parameter_ref_id:1, actual_value:1}, {2,1}, {3,1}]`; `pur_bags_type_id` unset → `20`.

## 8.5 Test script (post-response)

```js
var data = pm.response.json();
var id = data.id || data.entry_id;
if (!id) throw new Error('QC create failed: ' + pm.response.text());
pm.environment.set('pur_qc_id', id);
pm.environment.set('pur_qc_lines', JSON.stringify(reqBody.qc_details));
console.log('QC created: id=' + id + ' ref=' + (data.transaction_ref_no || ''));
```

Stores `pur_qc_id` (for PB's `qc_ref_id`) and `pur_qc_lines` (PB mirrors the QC lines). List QC is now a **pure read** like List PO/GP/GRN.

## 8.6 Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| `Missing QC deps: pur_po_id, pur_gp_id, pur_grn_id, ...` | Missing a previous hop — run the full **Discover → Create PO → Create GP → Create GRN** sequence first; read `pur_sniff_status` in the error. |
| `QC quality params unavailable in CQP - Create QC uses generic params` (Discover note) | Item has no active Purchase CQP on the tenant → generic [1,2,3] used (still chain-valid on fresh tenants). |
| `no active Purchase CQP found for item ...` / `CQP scan failed: ...` | CQP listing/detail GET failed or no match — check token/tenant, verify the item's CQP exists in ERP (Quality > Commodity Quality Parameter), or set `pur_qc_params` manually. |
| `bag type <n> from Packages row <m>` shows an unexpected value | Packages listing differs per tenant — the chosen row is the first/jute-named package; verify it's the bag type the business uses. |
| `no Packages rows` / `Packages scan failed: ...` | Packages GET failed — Create QC falls back to `20`. |
| QC 4xx/5xx on create | Stale `pur_*` (switch of tenant/POST without re-running Discover); or `qc_details` empty/mismatched vs the GRN's item/qty. Re-run Discover → PO → GP → GRN. |
| Stored QC's `item_type_ref_id` differs from `pur_po_item_type` | Observed on 795 (stored `113` on QC 2129) — the ERP can normalize item type at store time; not a payload error. |
| 401 on `/procure_to_pay/quality-control/` | Token expired or tenant changed — re-paste token + `tenant_id`. |
